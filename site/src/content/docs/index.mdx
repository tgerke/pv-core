## Why pv-core

<div class="landing-grid landing-grid--4">
  <div class="landing-card">
    <h3>Cases shaped by E2B(R3)</h3>
    <p>
      Reporters, patient, coded events with the six seriousness criteria, drugs,
      drug-by-event assessments, narrative. Versions are editable until the first signature
      and immutable after it; follow-ups and corrections are new versions.
    </p>
  </div>
  <div class="landing-card">
    <h3>Clocks derived, never maintained</h3>
    <p>
      Reporting rules are rows: destination, timeline, and a test over the case. Obligations
      materialize the moment a case is a valid ICSR; due soon, overdue, submitted,
      acknowledged, superseded, and waived are computed on every read.
    </p>
  </div>
  <div class="landing-card">
    <h3>Compliance as schema</h3>
    <p>
      A hash-chained audit trail written by database triggers, immutable signatures and
      submissions, signatures bound to the version hash, re-authentication to sign, and a
      runtime role that can only run DML.
    </p>
  </div>
  <div class="landing-card">
    <h3>Made for the R seat too</h3>
    <p>
      The web app consumes only the public API. The overdue queue, the DSUR line listing,
      and every derived view are one httr2 call or one read-only SQL connection away.
    </p>
  </div>
</div>
